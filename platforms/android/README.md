# Android native renderer

A thin OpenGL ES 2.0 shell around the frozen C ABI in
[`include/game_core.h`](../../include/game_core.h). All gameplay, camera, HUD and
text layout live in `libgame_core.so`; this directory owns a window, a GPU
context, the textures, an input loop, a speaker and nothing else.

### `gradlew`

`gradle/wrapper/gradle-wrapper.properties` pins Gradle 8.7, but
`gradle-wrapper.jar` and the `gradlew` scripts are **binary/generated files that
were not produced here** (no JDK+Gradle on the machine this was written on).
Generate them once with `gradle wrapper --gradle-version 8.7`, or open the
project in Android Studio. After that the commands below are literal.

## Build

```bash
cd platforms/android
./build_core.sh              # cargo build for arm64-v8a, armeabi-v7a, x86_64
./gradlew assembleDebug      # SDK+NDK build of libgame_jni.so, then the APK
```

* `./build_core.sh` is required **before** Gradle: `CMakeLists.txt` links
  `app/src/main/jniLibs/$ANDROID_ABI/libgame_core.so` as an imported library and
  fails with a readable message when it is missing.  Use
  `./build_core.sh arm64-v8a` while iterating.
* `./copy_assets.sh` copies `assets/dist/*.png` into `app/src/main/assets/`
  (falling back to `assets/sprites/*.png` when `assets/dist` is empty).  Run it
  whenever the art changes; it prints exactly what it packaged and warns about a
  missing sprite or a missing `font_atlas.png`.
* `./gradlew installDebug` or `adb install -r app/build/outputs/apk/debug/app-debug.apk`
  installs it; the launcher icon is the default (no icon resource is shipped).

## Run

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n com.gamecore/.MainActivity
adb logcat -s GameRenderer GameSurfaceView TextureStore Haptics MainActivity GameJNI
```

* **Left half** — floating move joystick (10 % radial dead zone, clamped to a
  14 %-of-min-dimension radius).
* **Right half** — floating aim stick: aim position in virtual units, plus
  `pointer_active`/`pointer_down`, so the core sees taps (menus, card picker).
* **Bottom-right square** — `GC_BTN_DASH`.
* **Back button** — toggles `GC_BTN_PAUSE` (the core's pause menu owns quitting).

## Design notes (the parts that are easy to get wrong)

### Command packing across JNI

`gc_cmd` is 56 bytes, 4-byte aligned, with this exact layout (asserted at compile
time in `game_jni.c` with `GC_ASSERT_LAYOUT`, and independently asserted by the
Rust core's own unit tests):

| offset | size | field | Kotlin access |
| --- | --- | --- | --- |
| 0 | 4 | `int32 kind` | `ints[i*4+0]` |
| 4 | 4 | `int32 sprite` | `ints[i*4+1]` |
| 8 | 4 | `float x` (centre) | `floats[i*9+0]` |
| 12 | 4 | `float y` (centre) | `floats[i*9+1]` |
| 16 | 4 | `float w` | `floats[i*9+2]` |
| 20 | 4 | `float h` | `floats[i*9+3]` |
| 24 | 4 | `float rot` (clockwise rad) | `floats[i*9+4]` |
| 28 | 4 | `uint32 rgba` (0xAARRGGBB, straight) | `ints[i*4+2]` (bit pattern) |
| 32 | 4 | `float u0` | `floats[i*9+5]` |
| 36 | 4 | `float v0` | `floats[i*9+6]` |
| 40 | 4 | `float u1` | `floats[i*9+7]` |
| 44 | 4 | `float v1` | `floats[i*9+8]` |
| 48 | 4 | `int32 flags` | `ints[i*4+3]` |
| 52 | 4 | `int32 _pad` | not copied |

`sizeof(gc_cmd) == 56`, `alignof == 4`.  Events are 3 floats + 1 int; status is
7 ints + 3 floats.  Kotlin mirrors these strides as
`NativeCore.FLOATS_PER_CMD`/`INTS_PER_CMD` and friends, and the wrapper clamps to
both array capacities, so a short array can never corrupt memory.

`GetPrimitiveArrayCritical` is used on the per-frame paths (array lengths are read
*before* entering the critical section, and the section contains nothing but a
copy loop), so a steady-state frame performs **no Java allocation**.

### One shader, one vertex layout

`aPos vec2` (virtual units) + `aUV vec2` + `aColor vec4` (straight alpha) and one
sampler.  `GC_CMD_RECT` is drawn with a 1×1 white texture bound and
`uUseTexture = 0`, so rects, sprites and glyphs share one program, one stride and
one attribute setup.

The virtual→pixel mapping needs only a scale, because commands are already in
screen space with the same origin and axis direction as the pixel space:
`pixel = virtual * gc_view_scale`.  There is no letterbox and no offset, so the
vertex shader is `aPos * uScale` followed by the unavoidable pixel→NDC step and
the y flip (the ABI is y-down, GL is y-up).  No matrix is needed.

**Colour is a per-vertex attribute, not a uniform** — that is what lets a run of
differently coloured rects/sprites collapse into a single draw call.

### Batching

Commands arrive in painter's order and are never reordered.  The renderer walks
them once and opens a new batch whenever `(texture, blend)` changes:

* texture: sprite PNG / font atlas / white (rects + shell overlay),
* blend: `GC_FLAG_FLASH` → `glBlendFunc(GL_SRC_ALPHA, GL_ONE)`, else
  `glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)`.

`GC_FLAG_SHADOW` is expanded on the CPU while batching: a black copy offset by
1.5 virtual units down-right is appended *immediately before* the real quad, so it
lands underneath within the same batch and costs no extra draw call.

All batches of a frame live in one growable direct `FloatBuffer`; the frame does a
single `glBufferData` and then one `glDrawArrays(GL_TRIANGLES, first, count)` per
batch, rebinding the texture/blend state only when it actually changes.  Rotation
is applied on the CPU:

```
[ c  -s ]      x' = c*dx - s*dy        (clockwise on screen in a y-down space)
[ s   c ]      y' = s*dx + c*dy
```

### Touch mapping

Screen pixels → virtual units is a division by `gc_view_scale`, i.e. exactly
`gc_pixels_to_virtual()` including its `<= 0 → 1` guard, so touch and the core
agree even before the first `gc_resize`.  Move stick: radial dead zone (10 % of
the radius), then the unit direction scaled by `min(len/radius, 1)`.  Pointer
**ids**, never indices, own a gesture.

Input state is mutated **only on the GL thread**: `GameSurfaceView.onTouchEvent`
copies the `MotionEvent` (`MotionEvent.obtain`), posts it with `queueEvent` and
recycles it after `HudInput` consumed it.  That is one small allocation per touch
event (not per frame) and it removes every data race with the renderer.

### Threading / lifecycle

`gc_create` is called on the GL thread in `onSurfaceCreated` (the core is
thread-affine to its creator) and every other core call happens there too.
`onSurfaceCreated` deletes the program, VBO and textures first, then rebuilds
them, so an EGL context loss is handled.  `onSurfaceChanged` calls `gc_resize`
with the physical pixel size plus the current insets in pixels, re-read whenever
`WindowInsets` change (`GameSurfaceView.updateInsets`, `(left, top, right, bottom)`).

Rendering is `RENDERMODE_CONTINUOUSLY`, which blocks in `eglSwapBuffers` on vsync
— no busy loop, no `Thread.sleep`, no `Choreographer` needed; `dt` comes from
`System.nanoTime()` and is clamped to 50 ms to survive a pause.

`onPause` saves before stopping the loop: `GameSurfaceView.saveNow()` posts
`performSave(synchronous = true)` to the GL thread and waits at most 250 ms, so
the blob is committed to `SharedPreferences` (base64, one key, file
`game_native_save.xml`) without risking an ANR.  Autosaves also happen every 5 s
and on every game-state transition.  The blob is restored inside `onSurfaceCreated`
right after `gc_create`.

### Audio / haptics

`Haptics.kt` maps all 14 `gc_event_type`s to a sound cue name
(`assets/sfx/<cue>.ogg`) and a haptic duration.  **No audio files exist in the
repository yet**: `loadSamples()` probes for them and registers what it finds, so
`playCue()` short-circuits on `sampleId == 0`.  Dropping the `.ogg` files into
`app/src/main/assets/sfx/` enables audio with no code change.  Haptics use
`VibratorManager` (API 31+) or `Vibrator`, gated on the `VIBRATE` permission and
`hasVibrator()`.

### Asset names are the core's, not ours

`nativeAssetNames()` returns `gc_sprite_file(0..GC_SPR_COUNT-1)` followed by the
`gc_font_atlas()` name, and `TextureStore` loads exactly that list.  Verified
against the current core: `player.png, enemy_a.png, enemy_b.png, gun.png,
bow.png, sword.png, money.png, xp.png` and `font_atlas.png` (1024×208).
`copy_assets.sh` checks for the same names.

Textures are decoded with `BitmapFactory` (`ARGB_8888`,
`inPremultiplied = false`) because `gc_cmd::rgba` is **straight** alpha, uploaded
with `GLUtils.texImage2D`, filtered `GL_LINEAR`, wrapped `GL_CLAMP_TO_EDGE`, and
the bitmap is always recycled.

## VERIFICATION STATUS

**Nothing in this directory has ever been compiled or run as an Android app.**
It was written on a Linux host with **no Android SDK, no NDK, no CMake toolchain,
no Android Gradle Plugin and no working Gradle**, and with no network access, so:

* `./gradlew assembleDebug` has **never been executed** — not even configuration
  (`settings.gradle.kts`/`app/build.gradle.kts` are unparsed by Gradle),
* `app/src/main/cpp/CMakeLists.txt` has **never been configured by the NDK
  toolchain** (it *has* been configured and built with the host toolchain, see
  below),
* `game_jni.c` has **never been compiled by the NDK's clang** (only by host
  gcc/clang, through the real CMakeLists.txt, against stub JNI headers),
* the Kotlin has **never been type-checked by kotlinc**,
* the shaders have **never been compiled by a GL driver**,
* nothing has been run on a device or emulator, so no frame has ever been drawn.

Treat every file here as reviewed-by-eye code until the first build.

### What *has* actually been executed: `host-selfcheck/`

Both self-tests link the **real, unmodified** `app/src/main/cpp/game_jni.c`
against a fake `JNIEnv` (plain C arrays):

```bash
cd platforms/android/host-selfcheck
./run.sh            # JNI wrapper vs. a fake core, then vs. the real core (900 frames)
./cmake_check.sh    # the real CMakeLists.txt: guard, configure, compile, link
```

* `test_pack` — a fake core with recognisable field values verifies the packing
  strides/slot order, independent clamping of the float and int arrays, null-handle
  behaviour, `gc_input` field order, status offsets, and the save grow-and-retry
  contract.
* `test_real_core` — the current `core/src/lib.rs` built as a host cdylib, then
  **900 simulated frames (≈15 s of gameplay)** driven through the JNI entry points
  exactly as `GameRenderer` does.  Result at the time of writing:

  ```
  900 frames: 136820 commands total, 427 in the busiest frame, 60 events
    kinds seen: sprite=1 rect=1 glyph=1 (shadow=1 flash=1), rotated cmds=10638
    distinct sprite ids used: 7/8, highest event type: 14
  ```

  Every emitted command was checked for a known kind, a valid sprite id, finite
  geometry, non-negative size, a valid glyph UV rect and no unknown flag bits;
  every event for a type in 1..14 with a finite payload; the status snapshot for an
  in-range state and hp within `[0, max]`; the save blob was round-tripped and a
  corrupted blob was rejected.

* `cmake_check.sh` runs the *real* `app/src/main/cpp/CMakeLists.txt` twice with
  the host compiler: first it must fail with the "Prebuilt core missing — run
  build_core.sh" guard, then — with a library in place — it configures, compiles
  `game_jni.c` with `-Wall -Wextra` **without a single warning** and links
  `libgame_jni.so`, which exports exactly the 15 expected
  `Java_com_gamecore_NativeCore_*` symbols.  It uses a throwaway ABI directory
  (`jniLibs/host-check/`) that is deleted again, so no host `.so` can be packaged.

  That run also produced a **finding that changes what the renderer must do**:
  `GC_CMD_SPRITE` commands carry `u0 = v0 = u1 = v1 = 0`.  A renderer that
  forwarded those UVs to the GPU would sample a single texel and draw every sprite
  as a flat colour.  `GameRenderer` therefore substitutes `(0,0)-(1,1)` for
  sprites and rects and uses the command's UVs only for `GC_CMD_GLYPH`; the test
  now asserts the core never starts carrying sprite UVs, so a semantics change
  fails the test instead of silently breaking sprites.

  What it does **not** cover: the JVM's discovery of the `Java_com_gamecore_...`
  symbols, `System.loadLibrary` on Android, GL/EGL, `BitmapFactory`, `SoundPool`,
  `Vibrator`, insets, Gradle, the NDK toolchain, or any rendering.

### Check these first, in this order

1. **`gradle wrapper --gradle-version 8.7`** (or open in Android Studio) — without
   it there is no `./gradlew` at all.
2. **ABI symbol names.** The `Java_` names in `game_jni.c` must match
   `com.gamecore.NativeCore`'s *instance* methods exactly.  `NativeCore.kt`
   deliberately does **not** use `@JvmStatic` (that would emit a static bridge with
   the same name/descriptor and make JNI auto-binding ambiguous).  If a test
   harness calls `javah`/`-h`, the expected names are
   `Java_com_gamecore_NativeCore_native<Name>`.
3. **`System.loadLibrary("game_jni")`** must resolve `libgame_jni.so`, which in
   turn needs `libgame_core.so` from the same `jniLibs/<abi>` directory in the
   APK (`unzip -l app-debug.apk | grep lib/` should list both for every ABI).
   A `UnsatisfiedLinkError` is shown as a Toast and logged, not a silent crash.
4. **Gradle/AGP DSL.** `packaging { jniLibs { keepDebugSymbols += ... } }`,
   `ndk { abiFilters += ... }`, `externalNativeBuild.cmake.path` and
   `buildFeatures { prefab = false }` are AGP 8.x; if AGP is newer, re-check them.
5. **The shader.** Compile status is checked and logged (`GameRenderer`,
   `"shader compile failed"`); a black screen plus that log line means the GLSL
   needs attention.  `uScale`/`uViewport` are `vec2`, `uUseTexture` is an `int`.
6. **`gc_abi_version()` vs. `EXPECTED_ABI_VERSION`.** Both `MainActivity` and
   `GameRenderer` refuse to run on a mismatch, by design.
7. **First frame on a device/emulator** — `adb logcat -s GameRenderer GameJNI`
   prints the loaded asset list (`assets: 8 sprites + font_atlas.png (1024x208)`)
   and every state transition.
8. **Rotation / cutout** — `gc_resize` must be called with the physical pixel size
   and the insets that `GameSurfaceView` reports; the shell must not letterbox.
9. **Pause/resume** — the save must land in
   `/data/data/com.gamecore/shared_prefs/game_native_save.xml` and a relaunch must
   restore it (`restored 16 bytes of save data` in logcat).
10. **16 KB page size** (Android 15+): `build_core.sh` links the core with
    `-Wl,-z,max-page-size=16384` and `CMakeLists.txt` does the same for the
    wrapper; verify with `llvm-readelf -l` on both `.so` files.  Set
    `GC_MAX_PAGE_SIZE_16K=0` to disable if the toolchain rejects the flag.

### Known gaps / honest caveats

* No launcher icon, no splash: the default Android icon is used.
* No automated UI test, no screenshot comparison, no emulator run.
* The `Choreographer`-based alternative for `dt` was not needed: continuous
  `GLSurfaceView` mode is vsync-blocked, which satisfies "never busy-spin".
* The two on-screen sticks and the DASH button are drawn by the shell
  (`GameRenderer.emitTouchOverlay`, quads only, `DRAW_TOUCH_OVERLAY`).  The core
  cannot know where the floating sticks are, so this is shell affordance, not game
  HUD — set the constant to `false` if the core is expected to draw them.
* `performSave` reads a 16-byte blob today; the retry loop handles a future blob up
  to 1 MiB.
* `host-selfcheck/run.sh` and `cmake_check.sh` compile against *stub* `jni.h` /
  `android/log.h` headers, so they prove the C source and the build wiring, not
  the NDK's own headers (the shapes used — `JNIEnv*` first argument,
  `(*env)->X(env, ...)`, `jintArray`/`jfloatArray`/`jbyteArray` — are standard).
* The core exports `gc_ui_button`, `gc_ui_slot`, `gc_ui_slot_count`, which are not
  declared in `include/game_core.h`.  The Android shell ignores them (the header is
  the frozen contract); if they are meant to be part of the ABI, the header needs
  them and `game_jni.c` would need forwarding shims.
